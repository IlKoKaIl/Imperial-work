## Daily Interview Protocol

Use this for every practice problem.

1. Restate the problem.
2. Ask clarifying questions:
   - What are input constraints?
   - Can values be negative?
   - Are duplicates possible?
   - Is the input sorted?
   - What should I return on empty input?
   - Are ties possible, and how should they be handled?
   - Can I mutate the input?
3. Give brute force first if helpful.
4. Explain the better idea.
5. Code in small chunks.
6. Test one normal case and one edge case.
7. State time and space complexity.

Say something every 30-60 seconds. If stuck, say:

> "I am stuck on the transition/edge case here. I am going to simplify the problem and test a small example."

If the interviewer gives a hint:

> "That helps. I think the hint is pointing toward X, so I will adjust my approach like this..."

## DP Template

When you see DP, say:

> "I am looking for overlapping subproblems and a state that captures the information needed for the future."

Then fill:

```text
State:
dp[i] means ...

Transition:
dp[i] = ...

Base cases:
dp[0] = ...

Order:
iterate i from ... to ...

Answer:
return ...

Complexity:
time O(...), space O(...)
```

Common DP patterns:

- Fibonacci style: `dp[i]` depends on `dp[i-1]`, `dp[i-2]`.
- Knapsack/coin style: choose or skip, often nested loops.
- Sequence style: `dp[i]` is best answer ending at `i`.
- Grid style: `dp[r][c]` comes from top/left or neighbours.
- Reachability style: maintain farthest reachable index or boolean state.

## Main DP Problem Types

When you read a DP question, first decide what kind of answer it wants.

| Type                    | Question wording                               | DP meaning                                                                                       | Examples in this plan                                    |
| ----------------------- | ---------------------------------------------- | ------------------------------------------------------------------------------------------------ | -------------------------------------------------------- |
| Counting                | "How many ways...?"                            | `dp[i]` stores the number of valid ways to reach/state `i`. Usually add possibilities.       | Climbing Stairs, Decode Ways                             |
| Minimising / maximising | "Minimum cost", "maximum profit", "best score" | `dp[i]` stores the best value up to/ending at `i`. Usually use `min(...)` or `max(...)`. | Min Cost Climbing Stairs, House Robber, Minimum Path Sum |
| Feasibility             | "Can you...?", "is it possible...?"            | `dp[i]` stores true/false reachability. Sometimes can be greedy instead.                       | Jump Game                                                |
| Sequence / subsequence  | "Longest..." or "best ending at each element"  | `dp[i]` often means best answer ending at index `i`. Compare against previous indices.       | Longest Increasing Subsequence                           |
| Coin / knapsack style   | "Fewest coins", "make target", "choose items"  | State usually includes an amount/capacity. Transition tries each choice.                         | Coin Change                                              |
| Grid paths              | "Path through matrix/grid"                     | `dp[r][c]` stores answer to reach cell `(r, c)`. Transition uses neighbours.                 | Minimum Path Sum                                         |

### What To Write Before Coding DP

Example for `House Robber`:

```text
State:
dp[i] = max money I can rob from houses 0..i.

Transition:
dp[i] = max(dp[i-1], dp[i-2] + nums[i])

Base cases:
dp[0] = nums[0]
dp[1] = max(nums[0], nums[1])

Order:
i increases from left to right, because each state depends on earlier states.

Complexity:
time O(n), space O(n), or O(1) if I keep only previous two states.
```

That is what `state`, `transition`, `base case`, `order`, `complexity` means.

## Traversal Coverage

Yes, this plan covers traversal algorithms.

| Problem                           | What it covers                    | Recursive or iterative note                                                                       |
| --------------------------------- | --------------------------------- | ------------------------------------------------------------------------------------------------- |
| Binary Tree Level Order Traversal | BFS on a tree using a queue       | Usually iterative, because level order naturally uses a queue.                                    |
| Validate Binary Search Tree       | DFS on a tree with value bounds   | Recursive is clean; iterative stack version is also fine.                                         |
| Number of Islands                 | DFS/BFS on a grid                 | Either recursive DFS, iterative stack DFS, or queue BFS. Iterative avoids recursion-depth issues. |
| Course Schedule                   | Graph traversal + cycle detection | DFS recursion with visit states is common; Kahn's BFS/topological sort is also strong.            |

Interviewer rule of thumb:

- If recursive is simplest, start with it and mention recursion depth.
- If input size could be large, say an iterative stack/queue avoids call-stack overflow.
- BFS is natural for shortest path or level-by-level traversal.
- DFS is natural for exploring components, recursion trees, and cycle detection.
- For trees, recursive code is often clearer. For graphs/grids, iterative DFS/BFS is often safer in Python.

## Binary Search Template

Say:

> "The key is defining the monotonic condition. Once the condition becomes true, it stays true."

```text
l, r = low, high
while l < r:
    m = (l + r) // 2
    if condition(m):
        r = m
    else:
        l = m + 1
return l
```

For rotated arrays, say:

> "At least one side is sorted. I will use that to decide which half can contain the target."

## Max Heap In Python

Python has a min heap, so use negative values for a max heap.

```python
import heapq

heap = []
for x in nums:
    heapq.heappush(heap, -x)

largest = -heapq.heappop(heap)
```
